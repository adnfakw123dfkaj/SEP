# AGENTS.md

## 1. 构建目标

在现有 TradingAgents 上按六条已批准需求扩展。仓库中的 `tradingagents/` 是应用根目录，README 和文档位于这里。本文是该应用后续编程任务的唯一治理入口。保持 LangGraph 的节点、边、执行顺序和辩论轮次不变。

## 2. 阅读顺序

1. 先读本文件。
2. 再读[架构文档](docs/architecture/architecture.md)，定位当前需求的接入点和共享边界。
3. 在[需求表](docs/req/requirements.yaml)中只读当前需求的条目，再读 `docs/req/` 中同编号的短记录。

一次只实现一条需求。行为以已批准的需求口径为准，JSON Schema 仅用于校验需求表格式。

## 3. 代码基线

以应用根目录下的现有代码为基线，在已有模块、状态和接口上扩展。沿用现有主图、CLI 和 Python API 执行路径。禁止重写主图或另建平行流程。

## 4. 可读范围、可修改范围、冻结范围

- **可读**　应用根目录的现有代码（含当前需求相关测试）、`docs/req/` 和 `docs/architecture/`。
- **可修改**　仅限当前需求已批准的文件，接入位置以架构文档为准。其他需求的实现和文件留待各自获批后处理。
- **冻结**　主图结构、六条已确认口径及旧结果目录 `results/`。旧基线目录中的数值不作实现或验收依据。
- **敏感原文**　密钥、请求头、完整 URL、工具原文和异常原文禁止复制到新增记录。运行指标使用已批准的安全配置字段、数据状态和错误类别。

## 5. 模块组织

| 现有模块 | 职责 |
| --- | --- |
| CLI `cli/` | 接收参数，启动分析，展示进度和已获准发布的结果。 |
| 图执行 `tradingagents/graph/` | 沿用现有 LangGraph 编排，负责状态传递、执行和检查点。 |

| 研究辩论 `tradingagents/agents/researchers/` 与 Research Manager | Bull/Bear 按原轮次辩论，Research Manager 汇总结论、未解决分歧和交接状态。 |

| 工具与数据路由 `tradingagents/agents/tools.py`、`tradingagents/dataflows/` | 调用供应商、应用数据窗口和请求级额度，提供取数结果及覆盖状态。 |

## 6. 集成契约

- **FR-03 计数与持久化**　一次模型调用只计一笔，使用单次调用 ID 去重。Token 缺失写 `unavailable`，实际 `0` 原样保留，SDK 内部重试标为「无法观测」。取数状态只作记录。交易记忆只在原成功路径写入，失败收尾只持久化已采集指标。
- **NFR-03 发布**　Portfolio Manager 产出候选后，在最终评级和受阻断范围内的内容发布前统一判定。硬 `REVIEW` 的最终评级必须是 `REVIEW`。审核时只阻断 Trader 的 `action`、`entry_price`、`stop_loss`、`position_sizing` 和结尾交易方向，以及 Portfolio 的 Executive Summary。各出口按同一规则处理这些内容。分析师报告、辩论长文和 Investment Thesis 保留原文。
- **FR-02 取数与失败**　关键数据须有可用 OHLCV 或已验证行情快照中的任一路，并有利润表、资产负债表和现金流量表三张可用报表。摘要和内幕交易不能补表，技术指标故障不单独终止运行。个股新闻、FRED、Polymarket 和 sentiment 沿用已批准的可选口径，全球新闻和内幕交易保持现有路由行为。关键数据缺失在研究辩论前统一失败，出口只披露原因，省略最终评级和交易内容。数据状态记录不得改写这条失败规则。供应商切换、Yahoo 重试和策略重试共用同一请求额度，具体次数留待批准。模型自由文本回退独立于该额度。
- **NFR-02 报告完整性**　缺关键数据沿用 FR-02 的失败结果，硬 `REVIEW` 采用 NFR-03 已判定结果。取数证据以指定 `as_of` 为截止。可选数据实际缺失才披露缺口，窗口未完整覆盖时，空结果仍是缺口。只有确认完整覆盖且结果为空才写「未检索到」。Markdown 和 HTML 报告头使用同一份信息，写明指定 `as_of`、实际采用的数据窗口及同一个带时区的生成时刻。各来源的细窗口留在数据状态中。
- **FR-01 研究交接**　只为研究辩论增加逐轮记录、未解决分歧和交接状态，沿用原长文与停止条件。分歧条目只记议题、双方观点、所引发言的轮次及角色。Research Manager 沿用一次自由文本回退，只有结论和分歧均可确认才标为完整。结论缺失时明确标注，并保留已记录的双方发言。共享辅助函数只提供回退和相关记录，最终 `REVIEW` 由发布护栏判定，交接不完整本身不触发。风险辩论沿用现有流程。
- **NFR-01 成本对比**　仅读取 FR-03 运行记录。同配置各跑 1 次仅采集 Token 和调用次数，不计入正式样本。正式对比要求两版各至少 3 个不同且同条件的运行 ID，实际数据覆盖只用于标记可比性。成本改善百分比和质量底线保持 `pending_baseline`，团队锁定且两项均满足后才可通过。耗时不作为通过条件。对比工作不改变应用运行策略。

## 7. 验证要求

实现顺序固定为 **FR-03 → NFR-03 → FR-02 → NFR-02 → FR-01 → NFR-01**。当前需求验收通过后，才开始下一条。

每条先提交计划并停止，列明需求编号、涉及文件及验收测试名。人工批准计划后才改代码。验收只用需求表为当前条目列出的测试名，使用离线替身并固定时钟。单独编写本治理文件时不运行这些测试。

## 8. 必须停下来询问的情况

遇到以下情况，说明需要改动的范围和原因，暂停相关工作等人工批准。

- 要修改冻结范围或已确认口径，或要改动 LangGraph 主图。
- 要填写重试次数、成本改善百分比或输出质量底线。
- 要扩大当前需求的可修改范围。
- 要删除或改写已有测试。
- 要记录密钥。
- 要新建本文件之外的治理文件。
